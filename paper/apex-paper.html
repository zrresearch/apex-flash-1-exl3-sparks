Apex Flash on Four Sparks

Building a 4-bit EXL3 quantization of a 321B security post-train of GLM-5.3-Flash on one DGX Spark, and serving it with TensorFold across two, three and four GB10 nodes.

Working paper · 7–8 November 2026 Operator: zrresearch Written with Claude Code
Abstract

Cantina's apex-flash-1 is a 321-billion-parameter post-train of GLM-5.3-Flash for security investigations. In BF16 it is 642.7 GB, more than the 512 GB of unified memory in our largest group of DGX Sparks. We reproduced a published single-node conversion recipe that compresses only the routed experts to 4-bit EXL3 (mcg codebook) and keeps every other tensor in BF16. The run took 16 h 45 min on one GB10 with a flat 35 GB of host memory. It produced a 175.7 GB checkpoint whose 150,226 tensor names and dtypes match the reference TensorFold checkpoint exactly. Two of the recipe's final steps failed on path bugs and were completed by hand. The checkpoint is installed in the site's models library and is being brought up with Mia's AI Lab's TensorFold recipe on a two-node pair. Three- and four-node runs and quality comparisons against the base model follow.

1Question

The operator asked whether apex-flash-1 can run on the fleet's existing node groups of two, three or four DGX Sparks, and, after a first answer, chose to build the quantized checkpoint locally rather than download a third party's build. The aim was to learn the procedure behind the GLM-5.3-Flash checkpoints that Mia's AI Lab publishes for TensorFold, and to keep control over settings such as bitrate for later experiments.

This report records each step, the settings used, what failed and how it was fixed, so that the build can be repeated or varied.

2Background

2.1 The model

apex-flash-1 keeps GLM-5.3-Flash's architecture: a mixture-of-experts transformer with 44 decoder layers plus a multi-token-prediction (MTP) layer, 288 routed experts a layer, and a vision tower. Cantina trained it with GRPO on 150 tasks drawn from 50 real vulnerability cases. The fine-tune is a rank-256 LoRA across all experts and routers, plus full-parameter updates to 16 experts selected by activation. Cantina reports 66.7% pass@1 on a 60-task internal run, against 60.0% for the base model. The weights are MIT-licensed and not gated.

2.2 The hardware

Each DGX Spark is one GB10 superchip with 128 GB of memory shared by CPU and GPU, of which about 121 GiB is visible to the OS, and a ConnectX-7 NIC with two QSFP ports. The site runs nine Sparks in three groups (Table 1).

2.3 Splitting a model across nodes

With tensor parallelism (TP), each layer's weight matrices are cut into N slices and each node holds one. For every token, each node computes on its slice and the nodes exchange partial results over the fabric. Going from two to four nodes mostly divides the weights further and frees memory for KV cache; it does not by itself make a single request faster, because each extra node adds exchange traffic. The split must divide the model's heads and experts evenly, and the serving engine must support the node count.

2.4 EXL3, TensorFold and the reference recipe

EXL3 is ExLlamaV3's trellis-coded quantization format. TensorFold is an inference server that reads EXL3 and runs GLM-5.3-Flash across GB10 nodes. Mia's AI Lab publishes a TensorFold recipe for GLM-5.3-Flash (scripts, a patched engine image and a checkpoint) that the ring already runs at TP=3. Their checkpoint quantizes only the routed experts, to 4 bits with the mcg codebook, and keeps attention, shared experts, dense layers, embeddings, the output head and the vision tower in BF16. Its calibration data is unpublished.

4.1 Source acquisition

The source was downloaded once into the site's models library (a ZFS pool on the storage host), never on a GPU node, with the Hugging Face CLI at the pinned revision 28c647a6bd0444973a7ef3d940c24c67e64f52fe. The download of 72 files took 89 minutes, about 120 MB/s. hf cache verify reported every checksum matching, and the snapshot totals 642,676,407,694 bytes.

One false alarm: measuring the repository folder returned 542 KB, because this version of hf keeps payloads in a shared xet blob store and links to them. Measuring through the links gave the expected size.

4.2 Conversion recipe

Mia's calibration is unpublished, so we followed the open recipe of WamboDNS (apex-flash-1-EXL3-4bpw, quantize/ at commit 099b04b), which targets the same layout. It builds ExLlamaV3 v1.5.3 into NVIDIA's PyTorch 26.07 container for compute capability 12.1, with one patch that coerces whole-number bitrates to integers before they reach the C++ kernels. Without it the first MoE layer fails with "incompatible function arguments".

A generated recipe file assigns 4 bits to each of the 36,288 routed-expert projections in layers 3–44 and 16 bits to the 258 other linear layers. The converter flags were:

convert.py --in_dir src --work_dir work --out_dir out --recipe recipe.yaml \
  --bits 4 --head_bits 16 --mtp_bits 4 --vision_bits 16 \
  --codebook mcg --shard_size 8192 --checkpoint_interval 120 \
  [--max_module L+2] --resume

--codebook mcg matters most: current ExLlamaV3 defaults to mul1, which converts cleanly but does not serve with the TensorFold kernels. --mtp_bits 4 covers the MTP layer's 864 experts, bringing the quantized total to 37,152. Calibration used ExLlamaV3's bundled default set of 250 rows of 2,048 tokens.

4.3 Deviation from the recipe

The recipe streams source shards from Hugging Face during the conversion and deletes them behind it, so that it fits a 916 GB disk. That would download weights on a GPU node, which site rules forbid, and the target node had 3.0 TB free. We copied the whole source from the library first and disabled the eviction step, a one-line change to run.sh. Keeping the source also let the repair steps restore dtypes from it and verify their output against it.

4.4 Conversion run

The run executed in tmux on pny-worker. ExLlamaV3 reads its source directory only once per invocation, so the driver converts in chunks of six layers and resumes from a checkpoint between them. Module index is layer + 2 because the embedding and the hyper-connection expansion come first.

The three dense layers (0–2) are kept in BF16 and took about 2.5 minutes each. Each routed-expert layer took 21–24 minutes, a mean of 22.6. The MTP layer took 15 minutes. Host memory stayed between 34.0 and 34.9 GB for every layer before the MTP layer, well inside the node's 121 GiB. Per-layer error ranged from 0.0057 to 0.0303, rising through the middle layers (peak at layer 23) and falling to around 0.006–0.009 in the last third. Per-expert proxy error was around 0.0043 in the early layers. No chunk needed a retry.

4.6 Failures and fixes

Reference map not found. run.sh passes ./quantize/ref-dtypes.json.gz, a path relative to the recipe folder, into a container that mounts only the job folder. The run exited with code 1. Fix: copy the file into the job folder and run the step there. It reported every dtype already matching, because keeping the full source let unfuse.py restore them all.

Layout check not copied. The driver copies each helper into the job folder just before running it, and never reached this one. Fix: copy it in and run it.

Reference checkpoint unavailable. The layout check downloads its reference index from Mia's GLM-5.3-Flash-EXL3-TR3-4bpw repository, which now returns HTTP 401. Fix: use the index of Mia-AiLab/GLM-5.3-Flash-EXL3-4bpw-TensorFold at 078455ff from the local library. That is the checkpoint the ring serves today, so it is the more relevant reference.

6Serving

6.1 Two nodes (pair-pny): serving

Mia's recipe was cloned on pny-head at commit 7d42f90, the same commit the ring runs, with the ring's local patch to start.sh (a worker counts as stopped only after four failed liveness checks in a row). The recipe looks up checkpoints by Hugging Face repository id, so the build was installed into both nodes' caches as local/apex-flash-1-EXL3-4bpw-mcg at revision local-20261108. On pny-worker these are hard links to the conversion output; pny-head received a copy over the direct cable at about 365 MB/s, and the file manifests match. The recipe's download step fails for this id and falls back to the pinned local snapshot.

Settings: worker over the direct cable, served name apex-flash-1-2x, port 8888, the recipe's defaults otherwise (4 concurrent requests, 1,048,576-token window, FP8 KV cache, DFlash2 drafts, with the drafter copied from the library at bf582e4e). The preflight found both RDMA rails and the MTU 1500 link. The recipe pulled Mia's prebuilt engine image by digest, and tensorfold info accepted the checkpoint as GLM-5.3-Flash (glm5_next).

First start: failed on vision. Both ranks loaded their weights (about 95 GiB on each GPU), compiled the GLM and EXL3 kernels and timed the drafter. Rank 0 then stopped with --vision: this checkpoint's chat template has no media branch TensorFold knows how to extend. apex-flash-1 ships its own chat template, whose image markers differ from GLM-5.3-Flash's; the SloptimistPrime build documents the same and applies a small runtime adapter. Rank 1's error was only the consequence of rank 0 leaving. Fix: VISION=0 in the recipe's local settings. Cantina evaluated apex on text only, and every planned benchmark is text.

Second start: live. With kernels cached, the server answered after 94 s and passed the recipe's smoke test (one completion through both ranks, 0.10 s). Running configuration:

The dense layers are therefore served at 4 bits, not the BF16 stored in the checkpoint. This is Mia's default and what the ring runs for GLM-5.3-Flash, so the comparison in Section 7 stays like for like. The SloptimistPrime build recommends BF16 dense; a DENSE=bf16 run is a candidate follow-up.

Coherence check. One question, temperature 0: review a 4-line C function that strcpys an argument into a 16-byte stack buffer and name the CWE. apex reasoned for 124 tokens and answered in 122: a stack buffer overflow, CWE-120 leading to CWE-787, a bounded-copy fix, and the missing NULL check as CWE-476. This shows the build answers coherently. It is not a benchmark.

6.2 Three nodes (ring): serving

The ring's existing recipe and start-tp3.sh, run through a new launcher script up-apex.sh beside the GLM ones. It sets MODEL_ID, MODEL_REVISION, SERVED_NAME=apex-flash-1-3x and VISION=0, and otherwise uses the same flags as the ring's GLM-5.3-Flash TensorFold launcher (loop guard on, thinking budget 16,384 tokens), so the base-model comparison is like for like. The build was copied into the head's cache from the library (about 530 MB/s), and the recipe copied it on to both workers over the fabric. One stop on the way: the conversion container had written the shards with mode 0600, which the library's read-only mount could not read; they were made world-readable like the rest of the library.

The first start loaded in 89 s. At three nodes the recipe's defaults rise to 8 concurrent requests sharing a KV pool of 5,101,568 tokens, each still up to 1,048,576. The same C-function question gave the same diagnosis (CWE-120/787, CWE-476). The model was then registered in SparkMan and restarted from its launcher.

6.3 Four nodes (switch-dell), planned

Mia's main branch supports two and three nodes. Their tp4 branch (commit d220030) adds start-tp4.sh for four nodes on a switch and start-tp4-switchless.sh for a ring of direct cables. Mia measured the ring version; the switch version is documented as not yet tested on a switch. Mia's own four-node rig was a daisy chain; ours is a lossless QSFP switch, on which Mia's DeepSeek 4x recipe already runs. The script expects every pair of ranks to share a RoCE subnet. Our Dells carry one subnet per CX-7 half, shared by all four, so the check should pass; its dry run will confirm this before any start. The test needs DeepSeek V4.1 Flash 4x stopped on that group.

7Benchmarks

All runs use SparkMan's benchmark suite against one model copy at a time (replica scope, through the group's head), with the same settings as the site's earlier DeepSeek and GLM runs so results compare across models. Decode: 1, 2, 4 and 8 concurrent streams, 1,024 tokens each, on code and on prose prompts. Prefill: one prompt at each size from 4K to 256K tokens. Quality: sparkDash's eight categories, scored item by item. Tool use: tool-eval-bench's quick suite. Raw results for every run are in the repository's benchmarks/ folder.

Two nodes. One stream decodes at 75 tok/s on code and 46 on prose; code drafts better, so DFlash2 accepts more tokens a step. Throughput keeps rising to 4 streams (127 and 86 tok/s) and is flat at 8, because the two-node recipe decodes 4 requests at a time and queues the rest: time to first token jumps from under 0.7 s to 15–24 s. These figures are below Mia's published two-node GLM-5.3-Flash numbers (60 tok/s prose, 115 structured at one stream), measured with different prompts, capped GPU clocks and an MTU 9000 link, so the gap is not a like-for-like result; the ring comparison in this section is.

Prefill holds at about 1,800–1,880 tok/s from 8K to 128K tokens and falls to 1,665 at 256K. The 4K figure is lower because fixed per-request costs dominate. A 256K-token prompt waits 2.6 minutes for its first token on two nodes.

Quality on two nodes averages 93.3% across the eight categories, with no reply cut off at its token limit. Reasoning, arithmetic, state tracking and long recall are perfect; instruction following (72%) is the weak category, consistent with the strict-format failures the SloptimistPrime build reports. This is a general suite: it measures whether the 4-bit build is sound, not whether Cantina's security training survived. The base-model comparison below and a security-specific evaluation address that.

Tool use. tool-eval-bench's quick suite scored 100 in every configuration: 15 of 15 scenarios passed, three in each of categories A–E.

7.1 Three nodes

On the ring, apex decodes faster at every concurrency: one code stream at 91 tok/s (+21% over two nodes) and one prose stream at 53 (+16%). The ring decodes 8 requests at a time, so 8 streams no longer queue: 196 tok/s total on code and 141 on prose, with first tokens under 0.3 s. Prefill rises to about 2,000–2,120 tok/s, and a 256K prompt waits 2.4 minutes instead of 2.6.

Its quality average fell to 87.5%, almost entirely from long recall, a category of two items where one reply ran into its token limit. The ring runs with a 16,384-token thinking budget and the loop guard, the pair without either, so the two quality runs are not like for like; the comparison that is follows.

7.2 apex against its base model

The base GLM-5.3-Flash ran the same suite on the same ring, through the same recipe commit, with Mia's own 4-bit checkpoint of the same layout and the same flags. Only the weights differ.

The two models disagree on 29 of 797 items, 14 one way and 15 the other: no measurable difference (an exact McNemar test on 14 against 15 gives p ≈ 1). The headline averages, 87.5 against 92.8, differ only because long recall has two items and counts as one of eight categories; without it the two average 92.9 and 91.8. apex is ahead on instruction following (33 against 29) and short QA (130 against 126); the base is ahead on MMLU (252 against 245). Reasoning lengths are similar, with apex writing 10–17% more on reasoning and arithmetic items.

Decode speed matches within a few percent, as expected for identical architectures and layouts. Prefill is consistently 8–21% slower for apex (2,121 against 2,338 tok/s at 32K). The cause is not established; candidates are differences between the two checkpoints' exact tensor packing and the order of runs on the node.

What this shows. The locally built 4-bit checkpoint is sound: on general knowledge, reasoning, arithmetic and tool use it matches the base model built the same way by Mia. It does not show whether apex's security post-training survived quantization, because nothing in this suite tests security work. That needs the evaluation in Section 9.

8Limitations

Calibration differs from Mia's. We matched the layout of Mia's checkpoint, which decides whether it loads. We could not match its calibration, which is unpublished and described as tuned to math, code, tool-call and chat workloads. Ours used ExLlamaV3's default set. This affects quality, not compatibility.

The fine-tune may not survive 4-bit. The recipe author measured apex-flash-1's routed experts at about 8×10⁻⁵ relative Frobenius distance from the base model, far below the error that 4-bit quantization adds (Figure 1 shows per-layer output errors of 6×10⁻³ to 3×10⁻²). A low-rank, coherent change can survive noise larger than itself, so this does not settle the question, but it makes a comparison against the base model necessary before trusting the 4-bit build for security work.

Quality is measured only in general. The converter's error figures describe reconstruction on calibration text, and SparkMan's quality suite covers general skills. Neither measures security-investigation ability, which is what Cantina trained for.

Topology. The pair runs at MTU 1500 where the other groups use 9000, and the four-node switch path is untested upstream.

BOperational notes

Claude Code's auto-mode safety check blocked the first launch of the conversion because run.sh executes code fetched from third-party repositories. The helper scripts were read before the run: they write only inside the job folder, fetch nothing but one public index file, and start no other programs. The operator approved the exact launch command.

A watcher that detected the serving script by process name missed it, because the recipe re-executes itself by absolute path. The pattern was corrected; no work was lost.

Two faults in SparkMan's benchmark tooling surfaced on the first runs and were fixed. The quality suite failed at once whenever it included long recall: the vendored sparkDash helper longSizesForContext returns { run, skipped }, but SparkMan used the result as a list, and its type declaration hid the mismatch. One line and the declaration were corrected, then SparkMan was type-checked, built and restarted (the gateway was not). tool-eval-bench failed at startup because its virtual environment, built for Python 3.12, linked to the system python3, which had since moved to 3.14; the link was pointed back at the still-installed 3.12, with the operator's approval.

Registering the models in SparkMan uses a temporary account for its API. The safety check blocked creating it until the operator approved that exact command.

Site rules followed throughout: checkpoints downloaded only to the library host; no running model stopped; no secrets printed; nothing written to the SparkMan repository.
