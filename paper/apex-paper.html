Apex Flash on Four Sparks

A 4-bit build of Cantina's security model, made on one DGX Spark and served across two, three and four.

zrresearch Nov 8, 2026

Cantina's apex-flash-1 is a 321-billion-parameter reinforcement-learning post-train of GLM-5.3-Flash for security investigations. In BF16 it is 642.7 GB, larger than the 512 GB of memory in our biggest group of DGX Sparks. We built our own 4-bit EXL3 version of it on a single Spark, in the same layout as the GLM-5.3-Flash checkpoints Mia's AI Lab publishes for TensorFold, and served it with their recipe on groups of two, three and four Sparks.

The conversion took 16 h 45 min on one GB10 and produced a 175.7 GB checkpoint whose 150,226 tensor names and dtypes match Mia's reference exactly. It loads unchanged in TensorFold. On four Sparks connected through a QSFP switch, a configuration Mia's four-node branch had not been run on, it decodes a single stream at 120 tokens per second on code and 70 on prose, and 262 tokens per second across eight streams. A 256K-token prompt reaches its first token in 103 seconds.

On a general quality suite of 797 items, the build is indistinguishable from the base GLM-5.3-Flash quantized and served the same way, and it scores 100 on tool use. On 4,710 security-knowledge questions the two also tie, 87.3% against 87.7%, and on 40 Cybench capture-the-flag tasks, three attempts each through three agent harnesses, apex solves 236 of 360 attempts against the base's 232, a difference within chance. Data, logs and configuration are in the research repository.

Speed on two, three and four Sparks

Each group runs the same checkpoint with TensorFold's tensor parallelism: every layer's weights are split into one slice per Spark, and the Sparks exchange partial results over their ConnectX-7 fabric for every token. We measured each group with SparkMan's benchmark suite under identical settings: decode at 1, 2, 4 and 8 concurrent streams of 1,024 tokens on code and on prose prompts, and prefill on single prompts from 4K to 256K tokens.

Single-stream decode rises with every Spark added, even though each one adds an exchange per layer. Decode on GB10 is limited by memory bandwidth, and each additional Spark reads a smaller slice of the experts for every token; at these sizes the smaller slice outweighs the extra exchange. Two Sparks decode four requests at a time, so their eight-stream figure is flat and queued requests wait 15–24 s for a first token. Three and four Sparks decode eight at once with first tokens under 0.3 s.

Prefill holds steady from 8K to 128K tokens on every group and dips only at 256K. Each group also ran on a different fabric, so these steps mix the effect of another Spark with the effect of the network.

Quality against the base model

A 4-bit build can load and run while quietly losing accuracy, and Cantina's changes to the base model are small next to the error that 4-bit quantization adds. To check the build, we ran SparkMan's quality suite (797 items in eight categories, scored item by item) on apex and on the base GLM-5.3-Flash. Both used the same three Sparks, the same recipe commit, the same flags and a 4-bit checkpoint of the same layout. Only the weights differed.

Both models scored 100 on tool-eval-bench's quick suite, passing all 15 scenarios, and so did apex on two and four Sparks. The build is sound on general knowledge, reasoning, arithmetic and tool use. None of this tests security work, which is what Cantina trained for.

Security evaluation

Cantina reports that apex-flash-1 solves 40 of 60 held-out vulnerability tasks against 36 for the base model. Those tasks are private, and the full-precision model does not fit our hardware, so we ask the question that matters for what we can run: does our 4-bit apex still beat the 4-bit base on security work? A gap of four tasks in sixty is about seven points; detecting it reliably takes hundreds of paired items.

We started with security knowledge: 4,710 multiple-choice questions from CyberMetric-2000, CTIBench's CTI-MCQ and SecQA (v1 and v2 test sets), asked with one prompt at temperature 0 with thinking enabled. apex ran on four Sparks and the base on three, at the same time; a second apex run on two Sparks measures how much answers move from the serving setup alone.

With an 8,192-token limit, both models often reasoned past the limit on CTIBench without answering: 501 questions for apex on four Sparks, 527 for apex on two and 574 for the base. We re-asked every such question with a 32,768-token limit, under a 16,384-token thinking budget on every server. About 57% of them then came back right in each run, and only 5 or 6 per run remained unanswered.

The two models are indistinguishable. Of 4,710 questions, apex alone answered 155 correctly and the base alone 177 (exact McNemar p = 0.25); on CyberMetric the split is exactly 25 each way. The base's small lead comes from CTIBench (p = 0.19). The second apex run, the same weights on two Sparks, scored 87.5%, between the two. It and the four-Spark run each answered correctly questions the other missed, 154 and 143 (p = 0.56); against the base, the two-Spark run splits 156 to 167 (p = 0.58). The same model on two serving setups disagrees on 297 questions, nearly as many as the 332 on which apex and the base disagree. The difference between the models is no larger than the noise from the serving setup.

This result does not settle whether the post-training survived. Cantina rewarded solving hands-on vulnerability tasks, not recalling security facts, so a model that kept every gain from its training could still tie on this test. It does show that the 4-bit apex has lost no security knowledge relative to the base. The test that can detect Cantina's gain is hands-on: capture-the-flag challenges run through the Codex agent harness that Cantina trained with.

Capture the flag

We use Cybench: 40 tasks from four professional competitions (HackTheBox Cyber Apocalypse 2024, SekaiCTF 2022 and 2023, GlacierCTF 2023, HKCert 2022), covering cryptography, web, reverse engineering, binary exploitation, forensics and miscellaneous puzzles. Each task gives the agent a short description, any handout files and, for 18 tasks, the address of a live service. A task counts as solved when the agent's final answer is the exact flag. We run the tasks unguided, with no hints or sub-steps, three times each per model, with a 45-minute limit per attempt.

We run every task through two agent harnesses. Codex is the harness Cantina trained apex with and recommends, so it measures apex as intended; it may also favour apex over a base model that has never seen it. Pi is a minimal harness, a short system prompt with read, write, edit and shell tools, that neither model was trained on. If apex leads under Codex but not under Pi, the lead comes from knowing the harness rather than from security skill.

Each attempt runs in its own Docker network with no route to the internet, the local network or the host. The agent works in Cybench's Kali Linux image, with every task's tools installed in advance and Cybench's copy of the answers removed. The challenge services join the same network with their ports unpublished, and a relay forwards one port to the model server. Everything is deleted after the attempt.

Cybench needed four repairs to run today. Its repository omits the nine GlacierCTF tasks (issue 789); we restored them from the competition's own repository with the patch posted in that issue. Eight challenge images are built on Debian releases whose package servers have moved to archive.debian.org, and one on a Java image since removed from Docker Hub; we changed only where packages are downloaded from. One service with three containers could start before its backend was reachable; services now restart on failure. We checked every handout for its real flag and found none.

Codex also needed adjusting: TensorFold accepts only plain function tools, so we turned off Codex's apps, plugins, browser, computer-use, image and sub-agent tools. That leaves the shell and file editing, identically for both models. In a dry run, apex solved a web task in 4 commands and a binary exploitation task in 19, writing a format-string exploit against the live service, and the base model solved a cryptography task in 3. Pi 1.4.0 needed no changes; it reaches the model over the chat completions API with thinking set to high, and it solved the same web task with apex and the cryptography task with the base model. OpenCode 1.19.4 uses the same API and thinking setting. Unlike the other two, OpenCode stops when the server answers that it is busy; 25 base attempts that ended this way at startup, during a few minutes when the base server was over its eight-request limit, were discarded and run again.

No harness separates the models. Under Codex apex solved 78 of 120 attempts and the base 76; under Pi, 81 and 77; under OpenCode, 77 and 79. Counted by task, apex did better on 8 tasks and the base on 5 under Codex (sign test p = 0.58), 5 against 3 under Pi (p = 0.73) and 4 against 5 under OpenCode (p = 1.0). Both solved about 30 of the 40 tasks at least once, and about 30% of attempts ran to the time limit for each model. With the nine attempts per task pooled, apex did better on 10 tasks and the base on 5 (p = 0.30). Codex, the harness apex was trained with, does not favour it more than the other two.

A time limit is not quite equal work. apex runs on four Sparks and the base on three, so apex generates more in 45 minutes: a median of 42,038 output tokens against 34,624 in the Pi attempts that reached the limit. Codex records usage only when an attempt ends, so it borrows Pi's ratio of 0.82. Counting an apex solve only if it came within 45 × 0.82 minutes, about 37 minutes, moves the difference to −0.8 points under Codex and +1.7 under Pi. OpenCode's capped attempts give a lower ratio, 47,720 tokens against 33,683, or 0.71, and a cut at 32 minutes moves its difference to −5.0 points, still within chance.

On these 40 tasks the 4-bit apex and the 4-bit base are indistinguishable. The intervals still allow a difference of up to about 10 points either way, so a gain the size of Cantina's reported one, about 7 points, can be neither confirmed nor ruled out. Pooling the three harnesses narrows the interval to about 5 points either way, and the difference stays near zero. NYU CTF Bench's 198 tasks follow, one attempt each through Codex.

Building the checkpoint

Why 4-bit

Each DGX Spark is one GB10 with 128 GB of memory shared by CPU and GPU, about 121 GiB of it usable. Only a 4-bit build fits every group.

FormWeights2 Sparks3 Sparks4 Sparks
BF16, as released642.7 GBnonono

EXL3, 4-bit experts~176 GByesyesyes
 Table 5. Which form of apex-flash-1 fits which group, before memory for the system and the KV cache.

EXL3 is ExLlamaV3's trellis-coded quantization format, and TensorFold is an inference server that runs EXL3 checkpoints of GLM-5.3-Flash across GB10 nodes. Mia's checkpoint quantizes only the 288 routed experts in each layer, to 4 bits with the mcg codebook, and keeps attention, shared experts, dense layers, embeddings, the output head and the vision tower in BF16. apex-flash-1 shares GLM-5.3-Flash's architecture, so a checkpoint in the same layout should load in Mia's recipe without code changes. That is the premise we tested.

Recipe

Mia's calibration data is unpublished, so we followed WamboDNS's open recipe, which targets the same layout. It builds ExLlamaV3 v1.5.3 into NVIDIA's PyTorch 26.07 container for compute capability 12.1, with one patch that turns whole-number bitrates into integers before they reach the C++ kernels; without it the first MoE layer fails. Every one of the 36,288 routed-expert projections in layers 3–44 gets 4 bits, and the 258 other linear layers keep 16.

convert.py --in_dir src --work_dir work --out_dir out --recipe recipe.yaml \
  --bits 4 --head_bits 16 --mtp_bits 4 --vision_bits 16 \
  --codebook mcg --shard_size 8192 --checkpoint_interval 120 \
  [--max_module L+2] --resume

The codebook flag matters most. Current ExLlamaV3 defaults to mul1, which converts cleanly but does not run on TensorFold's kernels. --mtp_bits 4 covers the 864 experts of the multi-token-prediction layer, for 37,152 quantized projections in all. Calibration used ExLlamaV3's default set of 250 rows of 2,048 tokens.

We changed one thing. The recipe streams source shards from Hugging Face during the conversion and deletes each one behind it, to fit a 916 GB disk. We had the room, so we downloaded the source once to our model library at a pinned revision, verified every checksum, copied it in full to the converting Spark and disabled the deletion. Keeping the source let the repair steps restore dtypes from it and check their work against it.

The run

ExLlamaV3 reads its source directory once per invocation, so the recipe converts six layers at a time and resumes from a checkpoint between chunks. The three dense layers stay in BF16 and took about 2.5 minutes each. Each routed-expert layer took 21–24 minutes, and the multi-token-prediction layer 15. Host memory stayed between 34.0 and 34.9 GB throughout, and no chunk needed a retry.

Serving it

We serve with Mia's TensorFold recipe for GLM-5.3-Flash, at the commit our three-Spark group already runs. The recipe finds checkpoints by Hugging Face repository id, so we installed the build into each head's cache under a local id and pinned revision. TensorFold accepted it as GLM-5.3-Flash. Every group uses the recipe's defaults: FP8 KV cache, DFlash2 speculative drafts, and dense layers quantized to 4 bits at load time, which is also how the base model runs, so comparisons stay like for like.

Two Sparks

The first start loaded both ranks and compiled the kernels, then stopped: apex ships its own chat template, whose image markers TensorFold's vision support does not recognise. Cantina evaluated apex on text only, and every test here is text, so we turned vision off. The second start answered after 94 seconds. Asked to review a four-line C function that copies an argument into a 16-byte stack buffer, apex named the stack overflow (CWE-120, leading to CWE-787), proposed a bounded copy, and flagged the missing NULL check (CWE-476). That shows the build is coherent; it is not a benchmark.

Three Sparks

The group's existing launcher ran apex with the same flags as its GLM-5.3-Flash service: loop guard on and a 16,384-token thinking budget. It loaded in 89 seconds and gave the same answer to the C question.

Four Sparks

Mia's tp4 branch adds a four-node launcher for a switch, written for but not yet run on one; Mia's own four-node rig was daisy-chained. The first start hung in NCCL initialization for 22 minutes, with all four ranks connected and idle. NCCL's bootstrap uses each node's default-route interface, here the 10 GbE management port, which the head's firewall closes to the other Sparks. Pinning the bootstrap to the ConnectX-7 fabric with SOCKET_IFNAME fixed it without a firewall change, and the group was live 271 seconds after the next start. Our three-Spark group never hit this because its settings already name the interface.

Limitations

Calibration differs from Mia's. We matched the layout of Mia's checkpoint, which decides whether it loads. We could not match its calibration, which is unpublished and described as tuned to math, code, tool calls and chat; ours used ExLlamaV3's default set.

The fine-tune may not survive 4-bit. The recipe's author measured apex's routed experts at about 8×10⁻⁵ relative distance from the base model, far below the 6×10⁻³ to 3×10⁻² output error that 4-bit quantization adds here. A low-rank, coherent change can survive noise larger than itself, so this does not settle the question, but it is why the comparison with the base model matters.

Fabric confounds group size. Each group size ran on a different network, so Table 1 mixes the effect of more Sparks with the effect of the fabric.

Multiple-choice tests measure recall. The security quiz tests what a model knows, not whether it can carry out an investigation, which is the skill Cantina trained. Its answers also depend on the thinking budget: with an 8,192-token limit, 11–12% of answers were cut off before a letter.

Forty tasks is a small sample. With three attempts at each of 40 Cybench tasks, only a large difference in solve rate between the models will be distinguishable from chance. Cybench's tasks are also public and their write-ups were published in 2023 and 2024, so either model may have seen solutions during training.

Single runs. Each speed benchmark ran once per configuration. Differences of a few percent in speed, or one or two items in a quality category, are within run-to-run variation.
